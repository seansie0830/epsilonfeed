# 分散式事務的終極救贖：二階段提交 2PC、TCC 補償模式與 Saga 長事務

> **迷因導讀**：單體架構時代，資料庫開個 `@Transactional` 註解，哪怕中途出 bug 也能優雅地全量 rollback 回滾；自從架構師把系統拆成三十個微服務，用戶在商城買了個手機：訂單服務扣了庫存、支付服務扣了用戶錢、積分服務網絡超時報錯！用戶看著銀行卡扣款成功但訂單列表空空如也，直接把客服電話打爆；後端工程師抱頭痛哭：「救命啊！我的錢在網絡光纖裡懸空了！」當微服務把單體巨石炸得粉碎，工程師才頓悟：原來世界上最遠的距離，不是生與死，而是支付服務已 Commit，庫存服務卻 Timeout，而你兜裡的年終獎正隨著資料不一致灰飛煙滅。

## 一、 ACID 在微服務中的崩塌：CAP 定理與 BASE 最終一致性

在單體應用（Monolith）的甜蜜歲月裡，軟體工程師享有數據庫巨頭們耗費數十年打造的溫室花園——關聯式資料庫的 **ACID 特性**（原子性 Atomicity、一致性 Consistency、隔離性 Isolation、持久性 Durability）。那時候的人生多麼純粹，只要在 Spring 框架的方法頂部輕輕敲下一行 `@Transactional(rollbackFor = Exception.class)`，底層的本地事務管理器就會默默接管資料庫連接 Connection，利用寫前日誌（WAL, Write-Ahead Logging）與 Undo/Redo Log 替你負重前行。哪怕你的業務邏輯在最後一步除以零拋出異常，資料庫引擎也能談笑風生間把所有變更瞬間抹平，宛如什麼都沒發生過。

然而，當系統並發量突破天際，CTO 大手一揮推行微服務與資料庫分庫分表（Sharding），「單一實體資料庫」的世界轟然倒塌。每個微服務都擁有了專屬的獨立數據庫實例（Database per Service），跨越物理節點與進程邊界。原本內存中的函數調用（In-Memory Call），全被置換成了不講道理的遠端過程調用（RPC）或 HTTP REST API。此時，電腦科學界最殘酷的物理法則——**CAP 定理（Consistency, Availability, Partition Tolerance）** 露出獠牙。

分散式系統的物理網絡永遠不可靠：交換機抖動、光纖被藍牙鏟車挖斷、GC 導致進程 STW（Stop-The-World）幾百毫秒。分區容忍性（P）是客觀現實，非選不可。於是工程師面臨靈魂拷問：你要強一致性（C），還是高可用性（A）？

如果強求跨網絡多節點的 **剛性事務（ACID）**，最經典的實作便是由 X/Open 組織制定的 **XA 規範二階段提交（Two-Phase Commit, 2PC）**：
1. **準備階段（Prepare Phase）**：協調者（Coordinator）向所有參與者（Participants）廣播：「大家都準備好提交了嗎？給我鎖定資源、寫好 Undo/Redo Log，然後回報！」
2. **提交階段（Commit Phase）**：若所有參與者都回覆「OK」，協調者廣播「Commit」；只要有一個節點超時或回覆「No」，協調者廣播「Rollback」。

```
[協調者 Coordinator]
       |
       |--- 1. Prepare (詢問並鎖定資源) ---> [訂單服務 Order DB] (行鎖鎖定、寫日誌)
       |--- 1. Prepare (詢問並鎖定資源) ---> [庫存服務 Stock DB] (行鎖鎖定、寫日誌)
       |--- 1. Prepare (詢問並鎖定資源) ---> [帳戶服務 Account DB] (行鎖鎖定、寫日誌)
       |
  (若全員成功)
       |--- 2. Commit (正式提交並釋放鎖) ---> [訂單服務 Order DB]
       |--- 2. Commit (正式提交並釋放鎖) ---> [庫存服務 Stock DB]
       |--- 2. Commit (正式提交並釋放鎖) ---> [帳戶服務 Account DB]
```

聽起來無懈可擊？但在高並發生產環境下，2PC 簡直是行走的災難製造機：
* **同步阻塞（Synchronous Blocking）**：在 Prepare 階段，所有參與節點的本地資料庫必須持有所涉及數據行的互斥排他鎖（X Lock）。直到 Commit 或 Rollback 完成之前，其他並發請求全被卡在隊列裡苦苦等待。數據庫連接池瞬間被打爆，系統 TPS（每秒事務數）直接雪崩。
* **單點故障與全局死鎖（Coordinator Single Point of Failure）**：一旦協調者在廣播 Commit 的中途突發崩潰（宕機），部分參與者收到了 Commit 指令完成了變更，另一部分參與者卻陷入無休止的等待與懸停狀態。更致命的是，那些手握行鎖的參與者根本不知道該提交還是回滾，所有共享資源被全局死鎖。哪怕重啟服務器，也需要人工介入搶救。

面對剛性事務的死局，現代分散式架構全面轉向 eBay 架構師提出、基於 CAP 中 AP 路線的 **BASE 理論**：
* **Basically Available（基本可用）**：分佈式系統出現不可預知故障時，允許損失部分可用性，例如流控降級或響應延遲增加。
* **Soft state（柔性狀態）**：允許系統中的數據存在中間狀態，並認為該中間狀態的存在不會影響系統的整體可用性（例如：訂單處於「處理中」而非「已完成」）。
* **Eventually consistent（最終一致性）**：系統中所有數據副本在經過一段時間的同步與補償後，最終達到一致的狀態。

微服務分散式事務的本質，就是從「夢想毫秒級全局強一致」的烏托邦，退守到「承認網絡會翻車、依賴柔性補償達成最終一致」的現實世界。

## 二、 主流分散式事務解決方案全景橫評

為了拯救在網絡懸崖邊搖搖欲墜的數據一致性，工業界發展出了五種核心武器。從依賴底層資源庫驅動的 XA 2PC/3PC，到業務代碼親自下場肉搏的 TCC、Saga，再到非同步解耦的消息隊列方案，各自具備完全不同的性能代價與複雜度基因。

### 1. 核心分散式事務模式深度橫向評測

| 維度指標 | XA 規範 2PC (兩階段提交) | 3PC (三階段提交) | TCC (Try-Confirm-Cancel) | Saga 狀態機長事務 | 可靠消息最終一致性 (如 RocketMQ) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **一致性保障等級** | 剛性事務（強一致性 CP） | 剛性事務（趨近強一致性） | 柔性事務（最終一致性 BASE） | 柔性事務（最終一致性 BASE） | 柔性事務（最終一致性 BASE） |
| **事務邊界與控制層** | 資料庫/驅動層（RM） | 資料庫/驅動層（RM） | 業務應用代碼層 | 業務應用/編排引擎層 | 消息隊列中間件 + 業務監聽器 |
| **資源鎖定範圍** | 全局鎖定，持續至 Commit | 引入超時機制，減少死鎖時間 | **僅在 Try 階段鎖定凍結資源** | **無全局鎖**，直接提交本地事務 | **無全局鎖**，純非同步解耦 |
| **高並發吞吐量 (QPS)**| 極低（< 500 QPS，鎖阻塞嚴重）| 較低（網絡 RTT 輪數多達 3 次）| 高（上萬 QPS，資源隔離顆粒度細）| 極高（適合長週期大跨度調用鏈）| 頂級（可達十萬級 QPS，極速削峰）|
| **業務代碼侵入度** | 極低（SQL 透明執行，框架接管）| 極低（SQL 透明執行） | **極高（需編寫 Try/Confirm/Cancel 3倍代碼）** | 中高（需為每個正向操作寫補償方法） | 低中（需編寫本地事務監聽器與校驗邏輯） |
| **網絡延遲敏感度** | 極其敏感，任何延遲皆拖垮連接池 | 極其敏感，3 次 RTT 延遲放大 | 中等，僅受 RPC 呼叫耗時影響 | 低，依賴異步事件驅動與狀態機推進 | 極低，完全非同步化發布與訂閱 |
| **懸掛與空回滾防禦難度** | 無需業務處理（底層引擎承擔）| 無需業務處理 | **極高（必須手工實作事務狀態防禦表）** | 中等（補償邏輯需保證嚴格冪等） | 低（消費端保持冪等去重即可） |
| **典型適用場景** | 銀行底層同構 DB 轉帳、傳統金融巨石 | 歷史實驗性方案，生產環境極少落地 | 核心電商秒殺下單、支付結算扣餘額 | 跨境機票酒店多段行程預訂、審批流 | 跨系統積分贈送、短信發送、數據快照同步 |

### 2. 三大現代主流方案架構深層解析

#### (1) TCC 模式：資源預留與二階段補償的性能怪獸
TCC 本質上是將資料庫層面的 2PC 搬到了**應用業務層**。它不再依賴資料庫的原生鎖，而是由業務代碼將資產拆解為「可用狀態」與「凍結狀態」：
* **Try（檢測並預留資源）**：完成所有業務檢查（一致性），預留必須的業務資源。比如用戶餘額有 1000 元，要買 100 元的東西，Try 邏輯不是直接扣減，而是將 100 元標記為 `frozen_balance = frozen_balance + 100`，此時可用餘額變為 900 元。
* **Confirm（確認執行業務操作）**：真正執行業務。不作任何業務檢查，只使用 Try 階段預留的業務資源。將 `frozen_balance = frozen_balance - 100`，並增加積分或完成下單。
* **Cancel（取消執行並釋放資源）**：釋放 Try 階段預留的業務資源。將 `frozen_balance = frozen_balance - 100`，還原可用餘額。

TCC 的優點是性能極高，鎖定資源粒度極小；致命缺點是**研發成本炸裂**，原本一個業務接口現在要寫 Try、Confirm、Cancel 三個方法，且 Cancel 必須承擔倒流一切的因果律武器，研發排期直接乘三。

#### (2) Saga 模式：化整為零的事件驅動長途列車
Saga 模式最早由 Hector Garcia-Molina 等人於 1987 年提出，專門用來處理解決長時間運行的事務（LLT, Long-Lived Transactions）。在 Saga 模式中，一個分散式長事務被拆解為若干個局部的子事務 $T_1, T_2, ..., T_n$。每個子事務 $T_i$ 都有一個對應的反向補償操作 $C_i$。

Saga 的核心執行法則如下：
* **正向順序執行**：$T_1 \rightarrow T_2 \rightarrow ... \rightarrow T_n$。只要每一步都成功，長事務圓滿完成。
* **異常回滾補償**：假若子事務 $T_k$ 執行失敗，Saga 協調器（Orchestrator）將以反向順序調用歷史所有已成功步驟的補償操作：$C_{k-1} \rightarrow C_{k-2} \rightarrow ... \rightarrow C_1$。

Saga 的特點是**沒有 Try 預留階段，第一階段直接提交本地數據庫事務**。因此性能極佳，不存在長時間資源鎖定。但也正因如此，Saga 犧牲了數據隔離性（Isolation）——某個子事務的變更在整個 Saga 尚未結束前就對外可見（引發髒讀或髒寫）。若業務允許「衝正」或「退貨」（如機票出票失敗後退回付款），Saga 是長鏈條微服務的最佳拍檔。

#### (3) 可靠消息最終一致性：異步解耦的扛把子
透過如 Apache RocketMQ 的 Transactional Message（事務消息）機制：
1. 訂單服務向 MQ 發送一條「半消息（Half Message）」（此消息對消費者不可見）。
2. 半消息發送成功後，訂單服務執行本地事務（寫訂單數據庫）。
3. 根據本地事務結果，訂單服務向 MQ 發送二次確認：Commit（消息可被消費）或 Rollback（消息刪除）。
4. 若中途網絡斷開，MQ 服務端會主動回查（Check）訂單服務的本地事務日誌。
5. 下游庫存或積分服務收到消息後扣減庫存。若扣減失敗，通過 MQ 不斷重試，直至成功或進入死信隊列（DLQ）報警。

## 三、 實戰中的幽靈問題：空回滾、冪等性與防懸掛

在紙面上推導架構總是歲月靜好，一旦將代碼部署到真實的物理網絡上，分散式網絡的三大幽靈——**超時重試、亂序到達、重複投遞**，會以各種扭曲的方式狠狠教訓盲目自信的工程師。

在以 TCC 與 Saga 為代表的補償型事務架構中，若沒有嚴密的狀態機控制，系統分分鐘會出現「資產不翼而飛」或「無限刷錢」的毀滅性事故。

```
   [客戶端 Client]
         |
    (網絡嚴重延遲)
    1. 發送 Try 請求 -------------------- (在網絡光纖裡遊蕩 5 秒) ------------> [庫存微服務]
         |                                                                      |
    (協調者判定超時)                                                               |
    2. 發送 Cancel 請求 ---- (走快車道 50ms 抵達) ----> 觸發 Cancel 方法 (空回滾！)   |
                                                          |                     |
    3. 遲到的 Try 請求 ----------------------------------+----> 觸發 Try 方法 (產生懸掛！)
```

### 1. 幽靈一：空回滾（Empty Rollback）
* **現象翻車**：某微服務在調用參與者的 Try 接口時，由於網絡抖動或參與者機器正在 GC，導致 RPC 調用超時。協調者誤以為服務不可用，立即發起回滾，調用參與者的 Cancel 接口。但事實上，該參與者的 Try 請求根本就**還沒到達**（或者連 TCP 連接都沒建立）。
* **災難後果**：如果參與者的 Cancel 方法直接盲目執行資產回退邏輯（例如：`balance = balance + 100`），那麼在用戶根本沒被扣錢的情況下，憑空多出了 100 元！這就是典型的空回滾套利漏洞。
* **避坑防禦**：參與者收到 Cancel 請求時，必須先校驗該事務 ID 是否已經成功執行過 Try 階段。若根本沒有該事務的 Try 記錄，Cancel 方法只能記錄「此事務已取消」，不得執行任何反向資金/資產補償操作。

### 2. 幽靈二：業務懸掛（Suspension）
* **現象翻車**：這是分散式系統中最陰暗的死角。接續上述場景，當 Cancel 請求已經到達並完成了「空回滾」處理後，那個在網絡擁堵的光纖中遊蕩了 5 秒的遲到 Try 請求，終於慢吞吞地到達了參與者節點！
* **災難後果**：如果業務代碼缺乏防備，Try 接口看到請求進來，欣欣然執行了資源凍結或扣除（`frozen_balance = frozen_balance + 100`）。但糟糕的是，協調者早已判定該節點回滾，**未來絕對不會再發送第二次 Confirm 或 Cancel 指令**！這筆被凍結的資金將永遠被掛起在內存與數據庫中，這便稱為「事務懸掛」。
* **避坑防禦**：Try 方法在執行前，必須先檢查是否已經執行過對應事務 ID 的 Cancel 記錄。若 Cancel 已經搶先執行，Try 必須立刻拋出拒絕異常，終止資源鎖定！

### 3. 幽靈三：重複調用與冪等性破防（Idempotency Failure）
* **現象翻車**：在網絡超時或 MQ 消費重試機制下，Confirm 或 Cancel、以及 Saga 的補償方法，極有可能被微服務調用 2 次甚至 10 次。
* **災難後果**：每次重試如果都直接執行加減庫存或轉帳操作，用戶買一次手機將可能被退款 5 次，直接把電商平台薅成慈善機構。
* **避坑防禦：唯一事務日誌表防禦架構**
解決上述三大幽靈的工業級通用解法，是在每個業務參與者的本地資料庫中，開闢一張 **`distributed_tx_log` 分散式事務控制表**，並將業務操作與日誌記錄包裝在**同一本地事務**中：

```sql
CREATE TABLE distributed_tx_log (
    tx_id VARCHAR(64) NOT NULL COMMENT '全域分散式事務唯一ID',
    action_type VARCHAR(16) NOT NULL COMMENT '執行階段: TRY, CONFIRM, CANCEL',
    status VARCHAR(16) NOT NULL COMMENT '狀態: SUCCESS, FAILED',
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tx_id, action_type)
) ENGINE=InnoDB;
```

#### 核心防禦狀態機邏輯：
1. **Try 階段**：
   * 開啟本地事務。
   * 查詢日誌表：`SELECT 1 FROM distributed_tx_log WHERE tx_id = ? AND action_type = 'CANCEL'`。
   * 若已存在 Cancel 記錄，說明發生了「懸掛反衝」，直接拋出異常拒絕執行！
   * 執行業務資源凍結，寫入日誌 `(tx_id, 'TRY', 'SUCCESS')`，提交本地事務。
2. **Confirm 階段**：
   * 開啟本地事務。
   * 查詢日誌表：若已存在 `CONFIRM` 記錄，說明為重複調用，直接返回成功（**冪等放行**）。
   * 執行正式業務變更，寫入日誌 `(tx_id, 'CONFIRM', 'SUCCESS')`，提交本地事務。
3. **Cancel 階段**：
   * 開啟本地事務。
   * 查詢日誌表：若已存在 `CANCEL` 記錄，直接冪等返回成功。
   * 查詢日誌表：`SELECT 1 FROM distributed_tx_log WHERE tx_id = ? AND action_type = 'TRY'`。
   * 若不存在 Try 記錄，說明 Try 尚未到達（或調用失敗），此時插入一條防懸掛日誌 `(tx_id, 'CANCEL', 'SUSPEND_GUARD')`，不執行任何資金回退，直接返回（**優雅處理空回滾並防禦懸掛**）。
   * 若存在 Try 記錄，執行資產解凍與衝正，寫入日誌 `(tx_id, 'CANCEL', 'SUCCESS')`，提交本地事務。

## 四、 結語：架構設計的精髓不在於追求不切實際的完美，而在於接納不完美並為失敗做好兜底

微服務架構的演進史，某種程度上就是一部工程師對「絕對完美」執念的祛魅史。

許多年輕工程師在接觸分散式事務時，總幻想尋找一把能夠通殺所有場景的「銀彈」：既要有單體架構下 2PC 般的強一致性，又要有百萬級的秒殺並發性能，還要代碼無侵入、零配置、自動容災。但物理規律冷酷無情：光速在光纖中有極限、網絡協議必然存在丟包、服務器必然會遭遇宕機。任何宣稱能夠完美兼顧「強一致性、無限並發、零延遲」的方案，本質上都是在販賣架構永動機的偽科學。

成熟的資深架構師，早已學會向現實妥協：
* 在涉及真金白銀結算的極核心銀行核心賬戶間，不惜犧牲吞吐量，老老實實採用嚴格的 **TCC 資源凍結** 或成熟的二階段提交，搭配昂貴的專線網絡；
* 在電商長鏈條導流、物流、機票酒店履約等業務中，果斷採用 **Saga 狀態機** 或 **消息最終一致性**，用暫時的柔性狀態換取系統極致的並發吞吐；
* 對於邊緣業務（積分贈送、統計分析、行銷卡券），甚至連可靠消息都嫌繁重，直接非同步事件廣播加定時對帳任務掃描。

架構設計的終極精髓，**從來不是在象牙塔裡追求不切實際的零失敗，而是深刻接納軟硬件世界的不完美，並用冷靜、克制的設計為每一次注定的失敗做好最底層的兜底防線**。

當你不再為網絡超時而焦慮失眠，而是從容地設計出嚴密的防懸掛狀態機、冪等性日誌表，以及每日清晨準時運行的非同步對帳修復 Job 時，你才真正跨越了平庸工程師與頂級系統架構師之間的鴻溝。
