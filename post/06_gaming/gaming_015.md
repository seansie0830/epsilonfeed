# 開放世界遊戲的流式加載（Streaming）：世界分區 World Partition、LOD 網格簡化與遮擋剔除

> **迷因導讀**：打開放世界大作時，你騎著快馬狂奔或者開超跑飆到時速兩百公里，突然整個大地變成一片慘白虛無、馬卡在半空中瘋狂蹬腿、旁邊的建築物像黏土一樣慢慢長出來；玩家拍桌狂罵「這遊戲穿模崩潰了！」圖形工程師在後台滿頭大汗：「大哥你跑太快了，硬碟讀取速度根本趕不上加載世界的速度啊！」這不是物理法則崩潰，而是遊戲引擎在後台手忙腳亂進行的一場「瞞天過海魔術秀」不幸穿幫。今天我們就來拆解遊戲界最硬核的空間雜耍：流式加載（Streaming）、世界分區（World Partition）、LOD 網格簡化與遮擋剔除。

## 一、 記憶體有限 vs 宇宙無窮：開放世界的空間幾何難題

玩過《電馭叛客 2077》（Cyberpunk 2077）初期主機版、或是《俠盜獵車手 V》（GTA V）早期機械硬碟版的玩家，肯定經歷過那個刻骨銘心的名場面：開著改裝超跑在夜城或洛聖都的繁華大道上以極速狂飆，突然眼前的一棟摩天大樓變成了彷彿 PS1 時代的灰色多邊形黏土塊；再下一秒，地板直接消失，整台超跑墜入無底深淵，重力系統陷入沉思，最後遊戲直接彈出「記憶體不足」或畫面瞬間凍結整整三秒。

玩家憤怒拍桌：「垃圾優化！退錢！」但如果你鑽進後台去看看遊戲引擎架構師的頭髮數量，你會發現他們已經在懸崖邊緣跳了幾十年的鋼絲。

### 1. 殘酷的硬體物理極限：虛擬記憶體預算（VRAM Budget）

現代開放世界遊戲的地圖動輒數十到數百平方公里。《碧血狂殺 2》（Red Dead Redemption 2）的新奧斯汀與西伊麗莎白、《薩爾達傳說：王國之淚》的海拉魯大陸加地底與空島，甚至《微軟模擬飛行》的整個地球。這些世界如果把所有高解析度紋理（4K Albedo、Normal Map、Roughness、Metallic）、幾何頂點（Vertices）、碰撞體網格（Collision Meshes）、NPC 骨骼動畫資料和音效完全毫無壓縮地放進記憶體，其總量動輒幾百 GB 甚至數個 TB。

然而，當代主流玩家的顯示卡顯存（VRAM）通常只有 8GB 到 16GB，PS5 / Xbox Series X 則是共享 16GB GDDR6 記憶體（扣除系統保留後，留給遊戲渲染和遊戲邏輯的通常只有 12.5GB 左右）。
這意味著一個殘酷的事實：**任何一個給定的渲染影格（Frame）中，能常駐在顯存裡的幾何與材質資料，頂多只能覆蓋玩家周圍半徑幾百公尺內的狹窄空間**。

$$VRAM_{Available} \ll Data_{WorldTotal}$$

如果遊戲引擎把整張地圖硬塞進記憶體，系統唯一能做的事情就是立刻觸發 OOM（Out of Memory）崩潰報警。

### 2. 視野距離（Draw Distance）與幾何洪峰的幾何級數暴增

為什麼視野距離（Draw Distance）是所有顯卡的惡夢？因為空間幾何遵循平方反比與圓形面積擴展定律。
如果一個遊戲只渲染玩家半徑 100 公尺內的物體，假設面積為 $\pi \times 100^2 \approx 31,415 \text{ m}^2$。當遊戲企劃興奮地說：「我們要讓玩家站在山頂俯瞰 5 公里外壯麗的城堡！」——將可視距離延伸到 5,000 公尺時，需要處理的空間面積暴增為 $\pi \times 5000^2 \approx 78,539,816 \text{ m}^2$。

面積直接暴增了 **2,500 倍**！
如果遠處的一棵樹有 5,000 個頂點，近處 100 棵樹是 50 萬頂點，GPU 算力還能談笑風生；但如果 5 公里內漫山遍野的 25 萬棵樹都按照原始高模渲染，頂點數將直接突破 **12.5 億個**。此時 GPU 的頂點著色器（Vertex Shader）和光柵化單元（Rasterizer）會當場燒穿，幀率直接跌成個位數。

### 3. 非同步資產加載線程與阻塞卡頓（Hitching）的生死時速

為了解決記憶體不夠的問題，引擎必須使用「動態流式加載（Streaming）」：玩家走到哪裡，硬碟就把哪裡的資料讀進系統記憶體，再非同步拷貝（Async DMA Transfer）到顯存中；玩家走過的地方，舊資料必須立刻從記憶體被標記並釋放（Unload/Garbage Collect）。

這場後台的搬運競賽牽涉到多個線程的極限配合：
- **主執行緒（Game Thread）**：負責遊戲邏輯、玩家物理輸入、碰撞偵測。
- **渲染執行緒（Render Thread）**：負責生成渲染指令（Draw Calls），提交給 GPU。
- **非同步加載執行緒（Async IO Thread）**：常駐背景，從硬碟（NVMe SSD 或老舊的 5400 轉機械硬碟）以 Chunk 為單位拉取壓縮封裝檔（如 Unreal Engine 的 `.pak` 或 `.ucas`）。

當加載速度跟得上玩家移動速度時，歲月靜好；一旦玩家駕著超跑或者開著噴射背包超速狂飆，硬碟讀取頻寬（IO Bandwidth）瞬間被榨乾。此時如果主執行緒必須同步等待某個關鍵碰撞網格（Collision Mesh）就緒才能判定玩家是否踩在地面上，主執行緒就會被迫**阻塞（Block）**！
這就是為什麼你會在老硬碟上體驗到嚴重的**「掉幀卡頓（Hitching / Stuttering）」**——遊戲畫面凍結了 200 毫秒，不是顯卡算力不夠，而是主執行緒在死等硬碟交貨！

## 二、 開放世界渲染架構世代進化全景橫評

為了在有限的顯存頻寬和算力下呈現浩瀚無垠的虛擬世界，圖形學與引擎工程師歷經了數十年的架構演進。從最粗暴的九宮格分塊加載，到傳統的階層式細節層次（HLOD），再到顛覆遊戲工業幾何渲染管線的虛幻 5（Unreal Engine 5）Nanite 虛擬微多邊形技術，背後是無數場軟硬體的極限博弈。

以下是開放世界空間管理與幾何渲染技術架構的深度維度對比：

| 技術架構維度 | 傳統九宮格加載 (Grid Streaming) | 階層式細節層次 (Hierarchical LOD / HLOD) | 虛幻5 Nanite 虛擬微多邊形技術 | 視錐與遮擋剔除 (Frustum & Occlusion Culling) |
| :--- | :--- | :--- | :--- | :--- |
| **代表引擎 / 作品** | 早期 Unreal 3/4、Unity 舊管線、GTA 早期版本 | 《刺客教條：大革命》、《電馭叛客2077》、UE4 後期 | 《電馭叛客2077》（部分外圍）、《黑神話：悟空》、UE5 大作 | 現代主流自研及商業 3A 引擎底層標配 |
| **空間劃分哲學** | 將地圖切成固定大小格子，維持以玩家為中心的 $3 \times 3$ 九宮格加載 | 近處獨立 LOD，遠處將幾十個物體動態合批（Batching）烘焙成低模 | 將高模切成 128 三角形群集（Clusters），按像素誤差動態流式投影 | 純幾何檢驗：不在攝影機視野內、或被前方遮擋者直接扔掉 |
| **顯存帶寬佔用** | **極不穩定**：過格瞬間大量資產集中加載，引發顯存頻寬尖峰（Spike） | **中等偏高**：除了原始 LOD 0 網格，還額外常駐多套烘焙好的低模資料 | **極低且恆定**：顯存只存儲當前視角需要的 Cluster，頻寬波形平滑 | **無額外顯存佔用**：利用深度緩衝區（Z-Buffer）或層次 Z 緩衝（Hi-Z）剔除 |
| **LOD 彈出瑕疵 (Pop-in)** | **嚴重**：物件瞬間整批出現，或紋理突然由模糊變清晰（Mipmap 穿幫）| **顯著改善**：遠處物體輪廓穩定，但近看切換時仍有明顯的「幾何抽搐」跳變 | **完全消除**：以亞像素級別進行連續幾何過渡，肉眼完全無法察覺 LOD 切換 | **無**：不改變物體幾何精度，只決定「畫」還是「不畫」 |
| **每幀渲染幾何頂點規模** | 約 **300 萬 ~ 800 萬頂點**（超過此規模 Draw Call 與光柵化暴跌）| 約 **1,000 萬 ~ 3,000 萬頂點**（得益於遠景合批減少 Draw Call）| **數十億至數百億原始多邊形**（被軟體/硬體光柵化為 2,000 萬微三角形）| 透過精準剔除，將傳入渲染管線的幾何圖元減少 **50% ~ 80%** |
| **存儲 IO 依賴特徵** | 強度依賴硬碟循序讀取能力，遇到隨機尋道時卡頓頻發 | 需要預先載入大量遠景烘焙網格，增加遊戲本體安裝磁碟容量 | **極限榨乾高速 NVMe**：幾何如同虛擬紋理般逐頁流式加載（Page Streaming）| 依賴 CPU / GPU 計算剔除幾何，對磁碟存儲完全零依賴 |
| **管線主要瓶頸** | 主執行緒 IO 阻塞、DMA 傳輸卡頓、顯存爆發式溢出 | 美術離線烘焙工時漫長、記憶體佔用膨脹、光影貼圖（Lightmap）接縫 | GPU 計算著色器（Compute Shader）算力與高速硬碟解壓頻寬 | 軟體剔除佔用 CPU 週期；硬體 Hi-Z 查詢延遲與誤判開銷 |

### 1. 傳統 LOD（Level of Detail）的痛：幾何跳變的「抽搐現場」

在 Nanite 問世之前，遊戲界通用了三十年的傳統 LOD 技術本質上是一種**離散妥協**。
3D 美術師在製作一把椅子或一棟建築時，必須親手做 4 到 5 個不同精度的版本：
- **LOD 0**：近距離看，50,000 個三角形，螺絲釘的倒角都清晰可見。
- **LOD 1**：距離 20 公尺，簡化為 15,000 個三角形。
- **LOD 2**：距離 50 公尺，簡化為 3,000 個三角形。
- **LOD 3**：距離 100 公尺以上，只剩 300 個三角形的火柴盒輪廓。

當攝影機向前推進時，引擎根據物體在螢幕上所佔的像素大小（Screen Size Percentage）計算切換閾值。但問題來了：物體從 3,000 面瞬間抽換成 15,000 面的那一瞬間，邊緣輪廓（Silhouette）會發生突變，這就是玩家常說的 **「Pop-in（彈出瑕疵）」**。
即便工程師發明了 **dither cross-fade（抖動交叉淡入淡出）**，利用透明度噪點遮罩讓兩個模型在 0.5 秒內半透明疊加過渡，但也因此付出了雙倍渲染像素（Overdraw）的慘痛代價。

### 2. 視錐剔除（Frustum Culling）與遮擋剔除（Occlusion Culling）的神仙合約

如果說 LOD 是「遠處的東西算便宜點」，那麼剔除（Culling）技術的哲學就是**「看不見的東西一律當作不存在」**。

```
       [ 攝影機視錐體 (Frustum) ]
              \       /
               \ 物體A (保留渲染)
  物體B (剔除)   \   /
  [視錐外剔除]     \ /
               [攝影機]
```

1. **視錐剔除（Frustum Culling）**：
   攝影機視野是一個由六個平面組成的平截頭體（Frustum）。引擎會為場景中每個物體生成一個簡單的**軸對齊包圍盒（AABB - Axis-Aligned Bounding Box）**或**包圍球（Bounding Sphere）**。只需進行簡單的向量點積（Dot Product）數學運算，就能在幾微秒內判定包圍盒是否在視錐外。不在視野內的幾百萬個物件，直接在 CPU 端被一刀切掉，連 Draw Call 都不會發給顯卡。

2. **遮擋剔除（Occlusion Culling）**：
   你站在一座高聳的摩天大樓面前，雖然整座城市的後半部都在你的攝影機視角正前方，但它們全被這棟大樓擋得嚴嚴實實。如果全送進 GPU 渲染，就是純粹浪費光柵化算力的 **Overdraw**。
   現代引擎利用**分層 Z 緩衝（Hierarchical Z-Buffer, 簡稱 Hi-Z）**或利用 CPU 多線程軟體光柵化（如 Embree / Umbra 系統），將低解析度場景深度快速渲染出來。當後方物體的包圍盒深度值大於前方遮擋物的深度值時，GPU 直接在早期深度測試（Early-Z）階段將其拋棄，拯救顯存頻寬於水火之中。

## 三、 現代遊戲地圖設計師的偷樑換柱神技

如果說圖形工程師提供的是冷冰冰的演算法底層，那麼關卡設計師（Level Designer）就是舞台上最高明的魔術大師。在硬體性能受限的年代，他們用一整套「物理欺騙法」，讓全世界玩家心甘情願地上當受騙。

### 1. 長廊轉彎與狹窄縫隙「擠門縫」：最經典的偽裝加載閘門

只要你玩過《戰神》（God of War, 2018）、《最後生還者》（The Last of Us）或者《古墓奇兵》，你絕對經歷過以下場景：
奎爺走到一個漆黑狹窄的岩石縫隙前，雙手扶著石壁，側著身子以極其緩慢的速度「一步一步蹭過去」；或者卡爾在《星際大戰 絕地：組織殞落》裡費力地推開一扇沉重的生鏽鐵門。

```
[ 區域 A：九界之湖高模 ] 
       │
       ▼ (玩家走入)
[ S 型狹窄石縫岩洞 ]  <--- 視線完全被遮擋！觸發區域 A 記憶體釋放、硬碟全力拉取區域 B
       │
       ▼ (緩慢側身穿過)
[ 區域 B：亞爾夫海姆神殿高模加載完畢 ]
```

你以為這是為了營造身臨其境的壓迫感或打擊沉浸節奏嗎？
**這背後根本就是一個偽裝的加載進度條（Loading Bar）！**

在關卡設計的空間幾何學中，這個狹窄 S 型通道有兩個致命的圖形學特性：
1. **視線完全被遮蔽**：利用前方的石壁，遮擋剔除演算法瞬間把身後龐大的「九界之湖」數十萬個物件一次性在記憶體中標記為可清理；
2. **強制鎖定玩家移動速度**：無論玩家手把怎麼狂推、跑步鍵按得多用力，人物穿過這道縫隙的物理時間被嚴格鎖定在例如 4.5 秒。這 4.5 秒，正是引擎後台非同步加載線程（Async IO）從硬碟把下一張大地圖（例如亞爾夫海姆神殿）的幾何網格與 4K 貼圖解壓縮並塞進顯存所需要的**最低生理安全時間**！

一旦你擠出石縫，視野豁然開朗，下一幅宏偉畫卷已經無縫躺在顯存裡等你了。設計師不費吹灰之力，就避免了畫面出現慘白 Loading 介面的尷尬。

### 2. 直升機跳傘降落：動態多尺度幾何網格的空中雜技

在《俠盜獵車手 Online》、《極地戰嚎》或各類吃雞遊戲（如《PUBG》、《決勝時刻：現代戰域》）中，從幾千公尺高空跳傘俯衝降落，是流式加載最容易「穿幫」的修羅場。

當玩家處於 3,000 公尺高空時，整張大地圖一覽無餘。此時引擎採用的是**「宏觀高度場地形網格（Heightmap Terrain）+ 預烘焙超低解析度衛星空照圖」**。這時你在地表上看到的房子，本質上只是貼圖上的一個黑色方塊像素，連多邊形都不是。

當跳傘時速達到 200 km/h 直線俯衝時，空間半徑急劇收縮。引擎內部正以毫秒為單位打一場瘋狂的戰役：
- **高度 1,500 公尺**：載入粗糙的幾何方塊（LOD 3 建築群外殼）。
- **高度 500 公尺**：開傘減速（這也是設計師精心計算的物理緩衝時間），硬碟開始載入建築物門窗、主要道路與植被（LOD 2）。
- **高度 50 公尺**：雙腳即將著地，主執行緒必須不惜一切代價在 100 毫秒內將地面碰撞網格（Collision Mesh）放入物理引擎（如 PhysX / Havok）。

如果你在老硬碟上跳傘，降落速度超過了硬碟 IOPS 上限，就會發生「人先著地、但地面碰撞體還沒加載出來」的慘劇——玩家會直接穿透地表，像幽靈一樣筆直掉進海平面以下的虛無空間（Void），最終被系統的安全防護代碼強制處死判定。

### 3. DirectStorage 與 PS5 高速 SSD：硬體架構帶來的流式加載範式革命

過去三十年，遊戲流式加載之所以要玩這麼多「擠門縫」、「坐電梯」、「漫長開門動畫」的花招，核心瓶頸在於**傳統存儲管線的極度低效**：

$$\text{SATA/HDD} \xrightarrow{\text{慢速讀取}} \text{CPU 內存} \xrightarrow{\text{CPU 核心解壓縮}} \text{顯存拷貝 (PCIe)} \xrightarrow{\text{GPU 渲染}}$$

在舊世代架構中，壓縮的遊戲資產必須先由硬碟讀進系統記憶體，然後耗費 2 到 3 個寶貴的 CPU 核心進行 zlib / Kraken 解壓縮，解完之後再經由 PCIe 通道拷貝到顯存。整套流程延遲高達幾十毫秒，頻寬頂多只有每秒幾百 MB。

而隨著 PlayStation 5 定製的高速 PCIe 4.0 SSD（未壓縮頻寬 5.5 GB/s，配合專屬硬體解壓縮晶片可達 8~9 GB/s）以及 PC 端的 **Microsoft DirectStorage API** 全面普及，遊戲儲存架構發生了盤古開天式的劇變：

```
[ NVMe SSD 儲存 ] 
       │
       ▼ (DirectStorage / 硬體解壓晶片)  <--- 繞過 CPU！頻寬達 8 GB/s+
[ GPU 顯存 (VRAM) 直接吞吐 ]
```

遊戲資產直接走 DMA（Direct Memory Access）通道，從 NVMe 硬碟直通顯存，解壓縮全部由專用硬體晶片或 GPU 計算著色器在微秒級完成！
這帶來的直接結果就是《拉捷特與克蘭克：時空裂縫》（Ratchet & Clank: Rift Apart）中那種震撼業界的「瞬間穿越維度」：
玩家穿過一個時空傳送門，前一秒是繁華霓虹的賽博朋克都市，**不到 1 秒鐘**之內，身後場景被徹底清空，整座幾十億多邊形的史前侏儸紀森林已經完全在顯存中構建完畢。長廊轉彎與擠門縫的時代，終於在高速存儲的物理暴力面前走向歷史終點。

---

## 四、 結語：虛擬世界的每一座宏偉山峰，都是工程師在微秒間進行的無縫魔術表演

下次當你再度握起手把，沉浸在荒野西部壯闊的日落下，或是在夜城細雨紛飛的霓虹街頭開著改裝跑車呼嘯而過時，請偶爾把視線從絢麗的畫面上移開，稍微想一想那個在你背後瘋狂運轉的隱形世界。

在你推動類比搖桿、轉動視角的一瞬間，有幾十萬個你看不到的多邊形，在百萬分之一秒內被數學向量一刀剪除；
在你疾馳掠過的每一寸土地下，有數百兆位元組的幾何頂點與貼圖數據，正沿著 PCIe 匯流排如同水流般瘋狂湧入顯存，隨後又在被你甩在身後時被無情地抹去釋放；
遠方山巔那座看似亙古不變的古堡，其實剛剛在你眨眼的瞬間，悄悄地用幾何集群更替掉了自己的三層外皮。

沒有無窮無盡的記憶體，也沒有真正能容納整顆星球的矽晶片。
我們所熱愛的這片廣袤虛擬宇宙，從來都不是靜止的實體，而是一群世界上最聰明的圖形工程師與地圖設計師，用數學極限、存儲頻寬與人類視覺暫留現象，在每秒鐘六十次的刷新率之間，為我們不知疲倦、驚心動魄地連續表演了幾十年的無縫魔術。
